# Agent Collab 共同協作規則

版本：0.1.0。每位人員與自己的主 agent 互動；主 agent 代表該人員協調與執行，沒有中央 Controller。

## 共同入口與事實來源

安裝後，從 repo 根的 `AGENTS.md` 開始。先讀 `docs/agent-collab/PROJECT.md`、`ITERATION.md` 與本規則。

| 位置 | 以這裡的內容為準 |
| --- | --- |
| repo 的 PROJECT.md | 引擎／版本、repo／分支、Linear 位置、驗證方式、聯絡責任人 |
| repo 的 ITERATION.md | 當輪目標、核可範圍、驗收條件、誰在何時核可 |
| Linear | 工單、負責人、依賴、工作範圍、協調、進度與交付連結 |
| GitHub | 程式與素材版本、PR、CI、獨立 review 紀錄、合併結果 |

不同位置以連結互相引用。任務 AC 是當輪目標的分解，不得擴張目標；改動核可範圍要重新取得相關人的裁決。各項目以自己的 repo 規則版本為準，升級透過 PR。

## 一輪授權

先與提出需求的人確認本輪目標、範圍、明確排除與可驗收結果，記錄到 ITERATION.md。`proposed`／空白／待確認不是核可；記錄核可人、時間與實際確認內容或可讀引用，不自行填入假授權。

核可一次後，範圍內的查詢、開單、分工、分支開發、修正、驗證、獨立 PR 審查、合併已設定開發分支與工程交付，都可自行續行，不逐步找人批准。同一輪的正常修正也不需要重新核可。

若提出的是輪次之外的新需求，先記為 proposed／backlog 並整理提案；不因建立提案就開始實作。scope 已核可的子工作可直接開始。

只在以下情況找對應的人裁決：擴大範圍、改變產品方向、專業取捨或代理無法協調的衝突。工具權限缺失時請必要的權限授予者處理，並繼續不依賴該權限的工作。不要默認所有問題都由主理人承擔。

## 開單前查核與協調

每次建立新工作前，先查相關 Linear 工單，包括已完成／交付的同目標工作，以及相關開啟中的 PR、共享工作範圍與依賴。資料查不到時說明缺口；沒有查詢結果不能宣稱「無衝突」。

把查到的工作連結與處理結論留在工單描述或協調紀錄即可，無需另建大型表格。

| 查核結果 | agent 的下一步 |
| --- | --- |
| 沒有相同工作或重疊 | 在已核可範圍內開單、開始 |
| 已有相同工作 | 關聯／沿用，確認現有負責人的範圍；不重複實作 |
| 有依賴 | 記錄前置工作，調整執行順序；可並行的部分先做 |
| 修改場景／檔案／介面重疊 | 在共享紀錄協調分工或先後；未協調好的重疊部分先停 |
| 需要產品取捨或無法協調 | 列出衝突、影響與有限選項，找相應的人 |

不能擅自接管他人的單、改他人的 AC，或覆蓋他人未提交內容。查核只能看共享紀錄，不能保證看見所有本機修改或排除同時開單。開始工作時公開目前範圍，重要範圍變更時更新；Godot 共用場景、資源與專案設定也包含在查核內。

## 開發與進度同步

用各自的分支工作，分支可採 `<成員>/<工單編號>-<簡述>`，以 PROJECT.md 的目標開發分支為基底。任何同步前先確認目前分支與工作樹；不要 reset、清除或搬走他人的未提交工作。

工單保留核可輪次引用、負責人、範圍、依賴、AC。開始、真正阻塞、範圍改變、PR 可審、交付時更新 Linear；一般開發不逐條指令刷進度。

未知資訊只阻塞依賴它的部分。技術前提失效時帶證據與選項升回決策，不默默改寫目標。團隊還未決定的共用場景、素材、玩法裁決責任人，先列待討論，不虛構角色分工。

## 驗證與獨立 PR review

先依 PROJECT.md 與工單 AC 驗證，保留實際命令、結果及必要的試玩／畫面證據。沒有執行就記未驗；CI 綠燈不代表遊戲體驗已被人接受。

PR 必須接受獨立審查，優先使用第二模型；沒有第二模型，用同模型新建的隔離 agent。隔離 reviewer 只收到目標、AC、待審 Head SHA、base／diff、相關程式與驗證證據，不繼承實作對話。可使用 REVIEW.md 的 prompt 與結果格式。

原對話自我檢查不算獨立 review。若工具無法建立隔離 context，讓其他成員／其獨立 agent 接手審查，不偽造 PASS。

主 agent 將 finding 分為：

- **本單 blocker**：違反既定 AC、實際正常路徑失敗，或有具體資安／資料破壞證據。修正並重新驗證／審查。
- **後續 backlog**：有益但不影響本輪完成定義，附理由與後續連結；不自動擴成新 AC。
- **忽略**：不成立、已處理或收益不足，留下簡短原因。

審查結果須記 `reviewed_head`、reviewer／模型與隔離方式、結論、finding 與證據位置。程式版本更動後，舊 review 不能直接套用；讓獨立 reviewer 檢查最新版本與修正。

## 合併與平台條件

主 agent 合併前重新讀 GitHub 的目前 Head、目標分支、CI 結果、review 與合併狀態，確認：

1. PR 仍在已核可範圍，依賴／重疊已處理。
2. 獨立 review 的 `reviewed_head` 等於目前 PR Head，沒有未處理 blocker。
3. 必要 CI 對應同一 Head 且成功；未配置驗證入口的程式 PR 先補妥驗證，不能用文件勾選取代。
4. GitHub 實際合併條件已滿足；目標分支／base 變動影響有效性時，更新差異與必要驗證／review。

通過後，可在已授權範圍內直接合併開發分支，無需再問一次。平台要求的 approval、status 或其他條件不得 bypass，也不得為了本單自行降級。

AI 隔離審查與 GitHub approving review 是兩件事。同一 GitHub 帳號的另一個模型不會變成另一位帳號 reviewer；PR 評論也不會自動變成 required status。若平台需要另一帳號核准，找具權限的成員完成。

本套件的 review 紀錄由代理核對，尚未提供伺服器強制 review gate。agent 主動檢查後執行普通 merge，不依賴 GitHub 原生 auto-merge。

## 工程交付與人的驗收

合併後把 PR、交付 commit／版本、取得方式、啟動／試玩步驟、已驗證項目與已知限制同步到 Linear。

工程完成與產品驗收分開：工程工作可進入團隊對應的 Done／已交付狀態，並明示「待人驗收」。若團隊將 Done 定義為人驗收後才關單，就先停在該團隊的驗收狀態。不要自行新增一整套狀態機。

人員驗收結果記入本輪紀錄：accepted、needs_changes 或 pending。同目標內的缺陷可以正常修正；新增玩法或擴大範圍需另提案。合併開發分支不授權對外發布、Steam 上架、購買服務或破壞性操作。

## 成員首次接手

主理人提供 repo／Linear 權限與 repo 內 HANDOFF.md。成員自己的 agent 讀入口與平台現況，確認工具可讀寫所需資源；設定一次後沿相同流程工作。

無需主理人的對話歷史、個人 memory、固定模型配置或中央程序。交接引用目前事實來源，不複製另一份容易過期的進度總表。
